# 阶段 1 详解：PDF → Markdown（mineru-textbook-to-md）

> 本文档解决什么问题：把"上传 PDF 到 MinerU 并拿到按章组织的 Markdown 文档包"这件事讲透——三种运行方式、分块计划怎么审、书签有缺陷怎么办、失败了怎么续跑、怎么识别服务端故障、质检看哪些字段。

前置工具：`mineru-textbook-to-md`（MinerU 云端 API + **本地书签语义分块**）。它不是一个"一把梭"的转换器，而是把「分块 → 上传 → 合并 → 拆分 → 出报告」拆成了可以分步审核、可以断点续跑的流程。

## 1. 安全与前置条件（先做）

- **授权**：上传到 MinerU 前，必须确认用户已授权上传该 PDF；产出仅限个人学习使用，不对外分发。
- **Token**：只从环境变量 `MINERU_OFFICIAL_API_TOKEN` 读取，**禁止打印、禁止写入任何文件**（包括总计划、脚本、日志）。
- **依赖**：`pypdf`、`requests`（`requirements.txt` 仅这两项）；建议先设 `PYTHONUTF8=1` 避免 Windows 控制台编码问题。
- **不要**用 `--force` 破坏已有产物，也不要在常规流程里使用 `--allow-unverified-split`——它只为一次"有意为之、已在文档中记录"的手工修复而存在。

```powershell
$env:PYTHONUTF8 = "1"
python -m pip install -r "<skill-root>\requirements.txt"
```

## 2. 三种用法

### 2.1 `--plan-only`：只生成本地分块计划（不上传、不需 Token）

```powershell
python "<skill-root>\scripts\run.py" `
  --pdf "<pdf>" --base-name "<书名>" `
  --split-by auto --plan-only `
  --output "<工作根>"
```

这一步**纯本地解析 PDF 书签**，产出 `00-MinerU分块计划.json`。它是"上传前最后一次低成本纠错机会"，务必人工审核（见 §3）。

### 2.2 正式上传解析（需 Token）

```powershell
python "...\scripts\run.py" `
  --pdf "<pdf>" --base-name "<书名>" `
  --split-by auto `
  --output "<工作根>"
```

工具会按书签语义分块，大文件自动切多块并按序合并；合并进 `full.md` 时保留各块对应的**源页范围注释**，便于后续把任意章节边界回溯到具体 PDF 页段。

`--split-by` 取值：`auto`（默认）、`part`、`chapter`、`section`。

### 2.3 `--from-full-md`：不重新上传，从已有 `full.md` 重拆

```powershell
# 1) 先 dry-run 看计划
python "...\scripts\run.py" `
  --from-full-md "<full.md 或文件夹>" --page-count <页数> --dry-run

# 2) 审完再真正执行；书签不可用时走正文标题路径
python "...\scripts\run.py" `
  --from-full-md "<full.md>" --page-count <页数> --split-by chapter
```

这条路径**不依赖 PDF 书签**，改为从 Markdown 正文的章节标题识别结构——是书签缺陷的官方解法（见 §4）。

常用开关：

| 开关 | 用途 | 注意 |
|---|---|---|
| `--dry-run` | 只预览计划边界，不落盘 | 审核通过后再去掉 |
| `--force` | 明确覆盖已有产物 | 只在源 PDF 变了 / 明确要重建时使用 |
| `--archive-output` | 干净重建拆分输出 | 会归档旧输出 |
| `--direct-download` | 绕过系统代理直连 CDN | 仅网络受限时使用 |
| `--overrides` | 指定 `chapter-overrides.json` | 定向修补个别边界 |

## 3. 分块计划审核要点

打开 `00-MinerU分块计划.json`，逐项核对：

| 字段 | 含义 | 审核要点 |
|---|---|---|
| `pageCount` | 源 PDF 总页数 | 与源文件一致 |
| `ranges` | 每块的**闭区间**页范围 | 相邻块必须首尾相接、严格递增、无重叠无缺口 |
| `boundaries` | 各块起止边界页（多一个结束哨兵） | 每个边界都应是**某个书签节点的起始页** |
| `method` | 分块方法 | 正常为 `pdf-bookmark-balanced` |
| `targetPages` / `maxPages` | 目标块大小 / 页数上限 | `ranges` 各块长度应接近 `targetPages`，且不超过 `maxPages` |
| `bookmarkCount` | 解析出的书签数 | 与 PDF 实际书签数一致 |
| `rangeNodes[].startNodes` | 每块的起始节点（kind / number / title） | 人工确认标题正确、没有把章切在正文中间 |

**核心原则（也是工具的设计原则）**：

- 有可用书签时，**边界优先落在书签起始页上**，尽量保持一章完整；不要按固定页数（200、400…）机械切分。
- 若某章太长会导致块超过 API 上限，改用它的**子级小节书签**作为合法切点，而不是"数到第 N 页就切"。
- 若连小节边界都无法满足上限，**停止上传并报告**这个超大的语义单元，等待人工决策。
- 固定页范围只是"PDF 完全没有可用书签"时**有文档记录的降级方案**。

真实样例（本项目）：

```jsonc
// 泛函分析讲义(第2版)上册：330 页 / 101 书签 -> 6 块，maxPages=60，targetPages=55
"ranges": [[1,55],[56,108],[109,161],[162,218],[219,275],[276,330]],
"boundaries": [1,56,109,162,219,276,331],
"method": "pdf-bookmark-balanced",
"rangeNodes": [ { "startPage": 162, "endPage": 218,
                  "startNodes": [ {"kind":"numbered","number":"","title":"§5 共枙空间、弱收敛、自反空间"},
                                  {"kind":"numbered","number":"5.1","title":"共轭空间的表示及应用"} ] }, ... ]
```

```jsonc
// 点集拓扑讲义：327 页 / 92 书签 -> 2 块，maxPages=200，targetPages=163.5
"ranges": [[1,163],[164,327]],
"boundaries": [1,164,328],
"rangeNodes": [ { "startPage": 164, "endPage": 327,
                  "startNodes": [ {"kind":"chapter","number":"第五章","title":"有关可数性的公理"},
                                  {"kind":"numbered","number":"5.1","title":"第一与第二可数性公理"} ] }, ... ]
```

> 注意上面泛函那段里 `"§5 共枙空间…"` 的"共枙"是原书 OCR 的识别结果，属**预期误差**，不影响分块边界判定，但精排阶段应改为"共轭"。

> **关于块数与粒度**：上面泛函样例（6 块，每块 ≤ 60 页）是**正式上传**时的分块；项目总计划记录的 `--plan-only` 预览结论则是"2 块：p1-161 / p162-330"。两者**不矛盾**，差异来自分块粒度参数——plan-only 那轮用工具默认粒度（约 163 页/块，与点集的默认结果同量级），正式上传时为降低单块解析失败风险把页上限调小到 60 页/块，于是按书签边界重算为 6 块。判断计划合格与否看的是**每个边界是否落在书签起始页**，而不是块的个数。

## 4. 书签缺陷处理（真实案例）

### 4.1 现象

某书的自动拆分**只出了 7 章**，而正文实际有 10 章。查看拆分预览与 `00-待人工复核.md`（旧输出）可见三类书签缺陷同时存在：

1. **章级书签缺失"第X章"前缀**——书签树里章的层级信息不完整；
2. **章名被拆断**——旧复核清单里出现 `### 第二章 拓扑空间与`（完整章名应为"拓扑空间与连续映射"），标题在书签里被截断；
3. **整章书签完全缺失**——旧复核清单从"第七章 紧致性"直接跳到"第九章 映射空间"，第八章（完备度量空间）没有任何书签条目。

结果：书签路径只能拆出 7 章（第二章…第九章），第一章与第八章漏掉，章序也不完整。

### 4.2 处置

不要试图手工修补 PDF 书签——改用**正文标题路径**重拆：

```powershell
python "...\scripts\run.py" `
  --from-full-md "<书名>/full.md" `
  --page-count 327 `
  --split-by chapter
```

重拆结果（当前生效版本）：

- 章节数 **10**，与正文一致；
- 每章置信度 **100%**，`00-待人工复核.md` 变为"未发现需要人工复核的章节边界"；
- 拆分方法记录为 `structure-tree:chapter`（对比书签路径的 `pdf-bookmarks:chapter`）；
- 旧输出**归档**而非删除：`.trash/20260917_165920/`（保留旧复核清单作为问题证据）；
- **后续 LaTeX 阶段一律以重拆后的 10 章为准。**

重拆后的章节表（节选）：

| # | 章节 | 页码 | 置信度 | 图片 | 缺失图片 |
|---:|---|---:|---:|---:|---:|
| 1 | 第一章 朴素集合论 | 16 | 100% | 0 | 0 |
| 2 | 第二章 拓扑空间与连续映射 | 60 | 100% | 1 | 0 |
| … | … | … | … | … | … |
| 8 | 第八章 完备度量空间 | 252 | 100% | 1 | 0 |
| 10 | 第十章 基本群及其应用 | 277 | 100% | 13 | 0 |

### 4.3 定向修补的备选方案

若问题只出在**个别边界**（而非整棵书签树不可用），优先用覆盖文件而不是整本重拆：在 `full.md` 旁放 `chapter-overrides.json`（或用 `--overrides` 指定），每条覆盖包含 `id` 或 `title`，外加 `startAnchor`、`startLine`、`startPage`、`skip` 之一，然后重跑。

### 4.4 判断顺序

```
章数与书签树/正文不一致？
├─ 只有个别章错位         -> chapter-overrides.json 定向修补
└─ 大面积缺章/章名断裂    -> --from-full-md --split-by chapter 走正文标题路径重拆
                             （重拆前把旧输出归档到 .trash/<时间戳>/，保留问题证据）
```

## 5. 断点重试机制

工具把每个分块的原始结果（ZIP 解包、Markdown、图片、layout JSON）保留在 `00-MinerU原始分块/` 下。

- 中途失败后**直接重跑同一条命令**即可：已完成的分块目录会被复用，**只重传缺失的页段**。
- 因此：**成功合并后不要删除 `00-MinerU原始分块/`**，它是续跑的唯一依据。
- 37.5 MB / 330 页这类大文件上传慢、偶发失败属正常，重试成本远低于重传全书。

## 6. 服务端故障识别与分块粒度调整

阶段 1 的失败**多数不是 Token 问题**，不要一失败就去怀疑/更换 Token。正确做法是先读错误信息分类：

| 现象 | 判断 | 对策 |
|---|---|---|
| 返回含 `please try again later` | 服务端**临时故障**（排队/限流/后端异常），与 Token 无关 | 稍后重跑；已完成分块自动复用 |
| 解析启动后**约 28 秒即失败** | 单块过大导致服务端解析超时/拒绝 | 缩小分块：**每块 ≤ 60 页**细分块后重试 |
| 某页段反复失败、报 `parsing failed` | 该块的模型兼容性问题 | 换模型版本重试；本项目实测：某块用 `vlm` 模型连续 3 次崩溃，改用 `--model-version pipeline` 后成功 |
| 下载失败 | 网络/代理 | 先保持系统代理；确需直连时再用 `--direct-download` |

> 代价提示：换模型是**有副作用**的——本项目中被 `pipeline` 模型救回来的那段（泛函分析 p162–218），其公式环境与其余章节存在**轻微风格差异**（pipeline 输出），阶段 2.2 需重点校对该段公式。凡是"绕过去"的修复，都要在总计划里记一笔，并在验收时重点抽查。

分块粒度经验：**60 页**是 API 侧比较稳的单块上限（泛函 330 页 → 6 块，`maxPages=60`）；书签条件允许时也不必强求切得一样大，目标是"块大小接近且边界都落在书签上"。

## 7. 质检要点

阶段 1 结束前，逐项确认：

1. **章数与书签树/正文一致**。看 `00-解析质量总报告.md` 的"章节数"与拆分预览表行数；不一致就回到 §4。
2. **边界严格递增**，无重叠、无缺口（对照 `00-MinerU分块计划.json` 的 `ranges` / `boundaries`）。
3. **图片引用全部有效**：质量报告中"缺失图片"应为 `0`。本项目实测点集拓扑"图片数 27 / 缺失图片 0"。
4. **待复核清单归零**：`00-待人工复核.md` 里的低置信度边界必须逐条处理（用覆盖文件或重拆）。
5. **公式抽查**：抽若干"公式密集页"（积分号、上下标、多行对齐是高频出错点）对照原 PDF，把确认的问题记入待校对清单，留给阶段 2.2 定点修复。
6. **记一笔到总计划**：章数、图片数、缺失数、分块数、遇到的故障与处置——后续所有工作都以总计划为准。
