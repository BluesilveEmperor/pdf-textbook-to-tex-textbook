# 流水线总览：PDF → Markdown → LaTeX → PDF

> 本文档解决什么问题：给出整套两阶段流水线的全貌——各阶段做什么、产出哪些文件、目录怎么组织、阶段之间交接什么、多本书如何统一管理。读完本文应能独立规划一个新书的转换任务。

## 1. 一句话概括

把一本授权的（通常是扫描图像型的）数学/理工教材 PDF，先转成结构化的 Markdown 文档包，再逐章转成可编译的 LaTeX 项目，最终产出排版规范的 PDF。

```
PDF ──[阶段1]──> Markdown 文档包 ──[阶段2]──> LaTeX 项目 ──> PDF
      mineru-textbook-to-md        pandoc + 两遍流程 + 定理族环境
```

## 3. 阶段一产物：Markdown 文档包

阶段 1 工具默认在**源 PDF 同级目录**下创建以书名命名的文件夹，所有产物都放在里面：

| 产物 | 说明 |
|---|---|
| `full.md` | 全书合并稿，块间保留来源页段注释，可回溯到原始 PDF 页范围 |
| `00-MinerU分块计划.json` | 上传前的分块计划（块方法、页数上限、目标块大小、书签数、每段闭区间页范围、边界起始节点） |
| `00-PDF书签分级目录.md` | 书签树导出（有可用书签时生成） |
| `00-章节拆分预览.md` | 章级拆分预览表：行号 / 页码 / 置信度 / 复核标记 / 字符数 / 图片数 / 缺失图片数 |
| `00-解析质量总报告.md` | 质量结论：模式、来源、章节数、标题数、图片数、缺失图片数、拆分方法、待复核章节数 |
| `00-章节映射.json` | 边界、目录与正文对齐记录 |
| `00-待人工复核.md` | 低置信度边界清单（无问题时会明确写"未发现需要人工复核的章节边界"） |
| `00-MinerU原始分块/` | 每个分块的原始 ZIP 解包、Markdown、图片、layout JSON。**成功合并后也不要删除**，它是断点重试的依据 |
| `images/` | 全书图片（去重后） |
| `NN-第N篇…/NN-第N章…/` | 篇 / 章文件夹（无篇级书签时统一归入 `99-未归类章节/`），每章含 `01-原文解析.md`、`02-解析质量报告.md`、`images/` |

> 实例（本项目两本书）：两本 PDF 均无篇级书签，章文件夹因此都在 `99-未归类章节/` 下，属工具的**正常归类**，不是异常。

## 4. 阶段二产物：LaTeX 精排项目

| 产物 | 说明 |
|---|---|
| `main.tex` | 主文件：`\documentclass` + `\input{preamble}` + `\frontmatter`(标题页/目录) + `\mainmatter` 中每章一对 `\chapter{章名}` + `\input{chapters/chNN}` |
| `preamble.tex` | 共享导言区：页面设置、数学宏包、图形、列表、定理族环境、超链接与交叉引用、`\bookinfo` |
| `chapters/chNN.tex` | 每章一个文件；**章标题只写在 main.tex**，章文件内只含 `\section` 及以下 |
| `images/` | 正文实际引用的插图（文件名沿用 MinerU 的哈希名） |
| `build/` | 编译产物：`main.pdf`、`main.aux`、`main.toc`、`main.out`、`main.log` |
| `build_work/` 或 `tmp_work/` | 转换工作区：`prep_NN.md`、`chNN_raw.tex`、`stats_NN.json`、辅助校验脚本、`convert.py` |

**关键约定**：正文图片用 `\includegraphics{文件哈希名}`，不带 `images/` 前缀——因为 `\graphicspath{{images/}}` 已指向图片目录。

## 5. 目录结构约定（示例布局：点集项目）

```text
<工作根>/
├── 00-总计划.md                          ← 多本书的总计划 + 进度跟踪表
├── <书名A>/                              ← 阶段 1 产物（工具 --output 生成）
│   ├── <书名A>.pdf                       ← 源副本
│   ├── full.md
│   ├── 00-MinerU分块计划.json
│   ├── 00-PDF书签分级目录.md
│   ├── 00-章节拆分预览.md
│   ├── 00-解析质量总报告.md
│   ├── 00-章节映射.json
│   ├── 00-待人工复核.md
│   ├── 00-MinerU原始分块/                ← 原始缓存（保留）
│   ├── images/
│   └── 99-未归类章节/0X-第X章…/          ← 章文件夹
│       ├── 01-原文解析.md                ← ★ 阶段 2 的输入
│       ├── 02-解析质量报告.md
│       └── images/
├── <书名B>/                              ← 结构同上
└── 03-latex/                             ← 阶段 2 产物根目录
    ├── <书名A>/                          ← LaTeX 项目
    │   ├── main.tex
    │   ├── preamble.tex
    │   ├── chapters/  (ch01.tex …)
    │   ├── images/
    │   ├── build/     (main.pdf / main.aux / main.toc / main.out / main.log)
    │   └── build_work/(prep_NN.md / chNN_raw.tex / stats_NN.json / convert.py)
    └── <书名B>/
        ├── main.tex
        ├── preamble.tex
        ├── chapters/
        ├── images/
        ├── build/
        └── tmp_work/
```

编号前缀约定：篇文件夹 `02-第二篇 …`、章文件夹 `01-第一章 总论`、章文件 `ch01.tex`——全部按**稳定的数字序号**排序，保证文件系统排序与书的阅读顺序一致。

> **关于这个布局的性质**：上图是**示例布局（取自点集拓扑项目）**，用来说明目录**约定**，不是所有项目的现状快照。实际项目常见两类偏离：
>
> 1. **项目根可能残留编译产物与脚本副本**——若编译时忘加 `-output-directory=build`，项目根会散落 `main.aux` / `main.log` / `main.pdf` / `main.toc` / `main.out`；脚本副本也可能被误放在项目根（本项目泛函项目根就残留过一份 `convert.py`）。收尾时按 `acceptance-checklist.md` §4.1 的判据清理。
> 2. **工作区产物清单是「理想集合」**——`build_work/` 与 `tmp_work/` 的实际内容因转换脚本实现而异：泛函项目的 `build_work/` 实测只含 `convert.py`、`chNN_raw.tex` 与辅助校验脚本，**没有** `prep_NN.md` / `stats_NN.json`（那两样是点集项目 `tmp_work/` 的形态）。**缺项不影响流程正确性**，只要实际存在的脚本、中间产物与原始缓存都保留即可。

## 6. 阶段间交接物（最重要的三件）

阶段 1 → 阶段 2 之间，转换脚本实际只依赖三样东西：

1. **`01-原文解析.md`（每章一份）** —— 逐章转换的输入。含 YAML 头、"## 原文"分隔、"## 第X章"章标题、`###` 级小节标题与定理段落。
2. **章文件夹下的 `images/`** —— 图片源。转换脚本按 `\includegraphics{images/<哈希名>}` 反查并复制到 LaTeX 项目的 `images/`。
3. **`full.md` 的章级结构** —— 用于校对章数与顺序；`--from-full-md` 重拆时它就是唯一输入。

> 因此：**改章、改边界只需重跑阶段 1；改排版、改定理环境只需重跑阶段 2。**两阶段之间以 `01-原文解析.md` + `images/` 为稳定接口。

## 7. 多本书的组织建议

1. **一个工作根目录 + 一份总计划文档**（如 `00-总计划.md`）。总计划至少含：
   - 输入清单表（书名 / 源文件 / 页数 / 书签数 / 体积 / 授权状态）；
   - 转换工具与版权约束（仅个人学习使用，不对外分发）；
   - 环境状态表（Python / TeX Live / pandoc / Token 是否已配置）；
   - 目录结构规划；
   - **执行阶段记录**（每阶段的真实统计与已知问题处置）；
   - 风险与对策表；
   - **进度跟踪表**（步骤编号 / 内容 / 状态 / 完成时间）。
2. **每本书的 LaTeX 项目独立成目录**，共享同一套 `preamble.tex` 骨架；若某书需要单独微调（行距、页眉页脚），只改自己项目内的副本，互不影响。
3. **每本书一个转换工作区**（`build_work/` 或 `tmp_work/`），不要混用；工作脚本与中间产物都放这里，项目根只留 `main.tex` / `preamble.tex` / `chapters/` / `images/` / `build/`。
4. **接续工作时先读总计划**，以其中的已确认决策为准，避免重复决策与返工。

## 8. 本项目实测规模（素材出处：`00-总计划.md`）

| 指标 | 泛函分析讲义(第2版)上册 | 点集拓扑讲义 |
|---|---|---|
| 源 PDF 页数 | 330 | 327 |
| 书签数 | 101 | 92 |
| 源文件体积 | 37.5 MB | 9.2 MB |
| 阶段 1 章节数 | 4 章 | 10 章 |
| `full.md` 体积（实测） | 约 631 KiB | 约 642 KiB |
| 阶段 1 图片引用 | 21 张，缺失 0 | 28 张，缺失 0 |
| LaTeX 章文件 | 4 个 | 10 个 |
| LaTeX 图片（最终） | 17 张 | 27 张 |
| **`theorem` 环境数** | 101 | 233 |
| `\label` / `\cref` | 426 / 217 | 452 / 423 |

> 说明：同一本书在不同阶段有**三种图片口径**，数值不必相等，不要把它们当成矛盾：
>
> 1. 阶段 1 质量报告字段"图片数"（打包进文档包的图片文件数）：泛函 19 / 点集 27；
> 2. 阶段 1 总计划表记录的"图片引用"（Markdown 正文中的引用次数，同一张图可能被引用多次）：泛函 21 / 点集 28；
> 3. 阶段 2 复制进 LaTeX 项目 `images/` 的实际文件数（去重后）：泛函 17 / 点集 27。
>
> 验收时只认两个硬指标：**缺失图片数为 0**、**PDF 上不出现 `[缺图 …]` 占位**。

> **关于 `full.md` 体积**：按磁盘实测填写（泛函 645,754 字节 ≈ 631 KiB；点集 656,916 字节 ≈ 642 KiB）。`00-总计划.md` 早期记录的 523 KB / 415 KB 属**阶段 1 首次合并时点**的值——点集拓扑在书签缺陷修复时用 `--from-full-md --split-by chapter` 重拆过，`full.md` 随之后来增大到约 642 KiB，故一律以实测为准。

> **关于"定理环境"口径**：表中 **`theorem` 环境数 ≠ 定理族环境总数**。
>
> - `theorem` 环境数：泛函 101 / 点集 233；
> - 定理族环境合计（含 definition / lemma / proposition / corollary / example / remark）：泛函 426 / 点集 452。
>
> 总计划表所列 6 类（定理 / 定义 / 引理 / 推论 / 例 / 注）之和为泛函 382 / 点集 452——泛函的 382 **未含** `proposition`（命题 44 个）。引用这些数字时务必写清口径。
